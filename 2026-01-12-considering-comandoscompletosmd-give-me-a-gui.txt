● Great question! Yes, speech-only commands will still work, but there's an important detail about latency:

  How It Works Now

  When you use speech alone (no gesture), here's what happens:

  1. Speech command arrives at FUSION
  2. FUSION waits for a potential gesture to fuse with
  3. If no gesture arrives, the timeout fires
  4. Command executes as normal speech-only

  The Latency Trade-off

  Looking at the fusion.scxml delays:

  Commands with 1500ms wait (fusionable):
  - zoom_in, zoom_out → Wait 1.5s for gestures
  - show_traffic → Wait 1.5s for gestures
  - get_directions → Wait 1.5s for gestures
  - forward, restaurants → Wait 1.5s for voice

  Commands with 0ms delay (immediate):
  - search_location, recenter_map, help, etc. → Execute immediately

  Impact on Your Demo

  ✅ Most commands: No delay, work instantly
  ❌ Fusionable commands: 1.5 second delay when used alone

  Example:

  User: "procurar Lisboa"          → Executes immediately (delay=0)
  User: "aproximar"                → Waits 1.5s (delay=1500), then zooms
  User: "aproximar" + SWIPE_UP     → Fuses immediately, zoom+pan up

  If This Is a Problem

  If the 1.5s delay is unacceptable for speech-only commands, we have two options:

  Option 1: Keep current fix, accept the delay for fusionable commands
  - ✅ Fusion works both ways (speech→gesture, gesture→speech)
  - ❌ 1.5s delay for solo zoom/directions/traffic commands

  Option 2: Reduce fusion window from 1500ms to 500ms
  - ✅ Faster speech-only execution
  - ❌ Harder timing for fusion (need better coordination)

  Option 3: Smart routing based on command type
  - Only route fusionable intents to FUSION
  - Route others directly to APP
  - More complex but optimal performance

  Which approach do you prefer for your presentation? The 1.5s delay is noticeable but might be acceptable if you're demonstrating fusion capabilities. 🤔
